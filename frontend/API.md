# Form API contract

What the applicant form sends, and what it needs back. This is the frontend's
side of the contract, written down so the backend can be built against it
without a meeting.

Terminology follows [`../CONTEXT.md`](../CONTEXT.md). Behaviour and copy follow
[`DESIGN.md`](./DESIGN.md).

Status: **agreed with the backend**. The decisions are collected at the end.

## Scope

One public page: the German applicant form. Two endpoints, both unauthenticated
and both write-only. The form never reads application data back, and there is no
endpoint the form needs in order to render.

The form is served as static files. Both parts sit behind one reverse proxy on
the same machine — `/` serves the form, `/api/` proxies to Spring Boot — so
requests are same-origin and **there is no CORS to configure**. The form sends
no cookie, no credentials and no custom request headers, so nothing else needs
a preflight either.

## Only four of six routes submit anything

The first field of the form offers six routes. Two of them never reach this API
as an application, because they need no staff involvement at all:

| Route selected by the applicant           | What happens                                |
| ----------------------------------------- | ------------------------------------------- |
| Bei #ichbinhier mitmachen (Aktionsgruppe) | Panel with an external link. No submission. |
| Fördermitglied werden                     | Panel with an external link. No submission. |
| Social Media                              | Application                                 |
| Redaktion / Öffentlichkeitsarbeit         | Application                                 |
| Rechtliche Unterstützung                  | Application                                 |
| Etwas anderes                             | Application                                 |

So `category` in an application is always one of four values. The two bypass
routes are only reported to `POST /api/v1/route-selections` (see below).

## POST /api/v1/applications

Creates one application.

### Request

```json
{
  "submissionId": "6f9619ff-8b86-d011-b42d-00c04fc964ff",
  "category": "SOCIAL_MEDIA",
  "name": "Anna Müller",
  "email": "anna@example.de",
  "weeklyTime": "HOURS_1_2",
  "about": "Ich arbeite seit drei Jahren in der Moderation …",
  "privacyConsent": true,
  "consentTextVersion": "2026-09",
  "website": ""
}
```

| Field                | Type    | Required | Constraint                                             |
| -------------------- | ------- | -------- | ------------------------------------------------------ |
| `submissionId`       | string  | yes      | UUID v4, generated by the client                       |
| `category`           | enum    | yes      | see below                                              |
| `name`               | string  | yes      | 1–120 characters after trimming                        |
| `email`              | string  | yes      | max 254 characters, must parse as an address           |
| `weeklyTime`         | enum    | yes      | see below                                              |
| `about`              | string  | no       | max 2000 characters; omitted or `""` when empty        |
| `privacyConsent`     | boolean | yes      | must be `true`                                         |
| `consentTextVersion` | string  | yes      | version of the consent text the applicant agreed to    |
| `website`            | string  | yes      | honeypot, always sent, always `""` from a real browser |

JSON is `camelCase` — the Jackson default, so no configuration is needed.

### Enums

`category`, four values:

| Wire value      | German label on the form          | `CONTEXT.md` term |
| --------------- | --------------------------------- | ----------------- |
| `SOCIAL_MEDIA`  | Social Media                      | Category          |
| `EDITORIAL`     | Redaktion / Öffentlichkeitsarbeit | Category          |
| `LEGAL_SUPPORT` | Rechtliche Unterstützung          | Category          |
| `OTHER`         | Etwas anderes                     | Category          |

`weeklyTime`, four values:

| Wire value     | German label on the form   |
| -------------- | -------------------------- |
| `HOURS_1_2`    | 1–2 Stunden                |
| `HOURS_3_5`    | 3–5 Stunden                |
| `HOURS_5_PLUS` | mehr als 5 Stunden         |
| `IRREGULAR`    | unregelmäßig, projektweise |

The wire values are machine codes on purpose. German labels live only in the
frontend's copy module, so the copy can be corrected without a database
migration — and `IRREGULAR` is why `weeklyTime` is not a number of hours.

### Response — 201 Created

```json
{ "applicationId": "a3f1c0de-…" }
```

`applicationId` is the only field the frontend reads. The confirmation screen
shows a fixed text plus the email address the applicant typed, so **the response
carries no date, no next step and no queue position**. See
[Confirmation](#the-confirmation-screen-needs-nothing-from-the-server) below.

### Idempotency

`submissionId` is generated once per submission attempt and stays the same
across retries. A repeated `POST` with a `submissionId` that already exists must
**not** create a second application; answer `201` again with the same
`applicationId`.

This is not about double clicks — the button disables itself. It is about a
mobile connection dropping after the request was received. Without it, staff
find duplicates in the dashboard, which is exactly the wasted time this project
exists to remove.

A unique index on `submissionId` is enough.

### Honeypot

`website` is a field hidden from humans by CSS and skipped by keyboard
navigation. A real browser always sends `""`.

When it is non-empty, the submission is from a bot. Answer `201` with a
throwaway `applicationId` and store nothing. Answering with an error tells the
bot what tripped it; answering with success does not.

The frontend cannot do anything else about spam — rate limiting per IP is the
backend's call. The form has no captcha by design: it would break the two-minute
promise and add a third-party processor to a German association's form.

### Consent

`privacyConsent` must be `true`; the form cannot submit otherwise, but the
backend should reject `false` rather than trust the client.

`consentTextVersion` records **which wording** the applicant agreed to. The
current value is `2026-09`. If the consent sentence in `DESIGN.md` is ever
corrected, the version changes, and applications submitted before the change
remain attributable to the old text. Without it there is no way to answer what a
given applicant actually consented to.

The backend should stamp the consent timestamp itself using server time. The
frontend deliberately does not send one — a timestamp from the client's clock
is worth nothing as a record.

## POST /api/v1/route-selections

Reports which of the six routes an applicant picked, at the moment they pick it.

```json
{ "route": "COMMUNITY" }
```

| Wire value          | German label                              |
| ------------------- | ----------------------------------------- |
| `COMMUNITY`         | Bei #ichbinhier mitmachen (Aktionsgruppe) |
| `SUPPORTING_MEMBER` | Fördermitglied werden                     |
| `SOCIAL_MEDIA`      | Social Media                              |
| `EDITORIAL`         | Redaktion / Öffentlichkeitsarbeit         |
| `LEGAL_SUPPORT`     | Rechtliche Unterstützung                  |
| `OTHER`             | Etwas anderes                             |

Response: `202 Accepted`, empty body. The frontend sends this fire-and-forget
and ignores both the response and any failure — a broken counter must never
affect an applicant.

**No personal data, no identifier, no IP association, no cookie.** One counter
per route value is the entire feature.

### Why this endpoint is worth its cost

`A5` — that roughly four in five requests want the community rather than
association work — carries the whole design of this project, and
[`../docs/DISNEY.md`](../docs/DISNEY.md) admits it cannot be checked: the client
does not answer, and the two bypass routes currently leave through an external
link without leaving a trace.

This endpoint turns the project's central assumption into an observed number,
for one field and one counter. Without it, `A5` is still an invention at the
final presentation.

## Errors

`application/problem+json`, [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457).
Spring Boot 3 produces this shape natively via `ProblemDetail`.

```json
{
  "type": "https://ichbinhier.eu/problems/validation-failed",
  "title": "Validation failed",
  "status": 400,
  "code": "VALIDATION_FAILED",
  "errors": [{ "field": "email", "code": "EMAIL_INVALID" }]
}
```

The frontend renders German text looked up by `code`, and places each entry in
`errors` under the named field. **Do not send German messages** — the wording is
specified in `DESIGN.md` and reviewed in one place in the frontend; a message
composed in Java would bypass that review and drift in tone.

Field codes the frontend handles:

| `code`                                              | Field            |
| --------------------------------------------------- | ---------------- |
| `NAME_REQUIRED`, `NAME_TOO_LONG`                    | `name`           |
| `EMAIL_REQUIRED`, `EMAIL_INVALID`, `EMAIL_TOO_LONG` | `email`          |
| `CATEGORY_REQUIRED`, `CATEGORY_UNKNOWN`             | `category`       |
| `WEEKLY_TIME_REQUIRED`, `WEEKLY_TIME_UNKNOWN`       | `weeklyTime`     |
| `ABOUT_TOO_LONG`                                    | `about`          |
| `CONSENT_REQUIRED`                                  | `privacyConsent` |

Top-level codes:

| Status        | `code`              | Frontend behaviour                              |
| ------------- | ------------------- | ----------------------------------------------- |
| 400           | `VALIDATION_FAILED` | inline errors from `errors`                     |
| 429           | `RATE_LIMITED`      | one general message, submission stays retryable |
| 500, 502, 503 | `INTERNAL_ERROR`    | one general message, submission stays retryable |

An unknown `code` falls back to the general message. Adding a code therefore
never breaks the form — but it does mean the applicant sees generic wording, so
tell the frontend when the list grows.

The frontend also treats a timeout or a network failure as retryable, keeping
the entered values. An applicant never loses what they typed.

## The confirmation screen needs nothing from the server

Worth stating explicitly, because it removes work from the backend and it
changes what `DESIGN.md` originally asked for.

The confirmation screen shows one fixed text for all four categories, plus the
email address the applicant entered. The **concrete next step lives in the
auto-reply email**, not on the screen. That means the backend owns:

- the date of the next intro session,
- the different wording for `LEGAL_SUPPORT` (an individual appointment rather
  than the intro session),
- the honest waitlist message when there is no room.

The frontend cannot express any of these — the screen has no branch for them.

**The confirmation email is a requirement, not an improvement.** The page
subheading (`DESIGN.md` section 15) and the confirmation screen both tell the
applicant that an email with the next step is already on its way. If no email
arrives, the form makes a false promise twice on one screen, and the applicant
is back in the silence that `A8` describes — the failure this whole project
exists to remove.

The backend owns the email and will build it. Until it exists, the promise on
the screen is unbacked. If the email cannot be ready for the demo, the copy in
`DESIGN.md` sections 15 and 30 has to change first.

There is deliberately no endpoint for reading the next intro session date. The
form must render and submit with the backend's read side completely absent.

## Configuration

The frontend takes one build-time variable:

```
VITE_API_BASE_URL=http://localhost:8080
```

Unset in development means requests go to the Mock Service Worker instead of a
real backend, so the form can be developed and demonstrated before the backend
exists.

## Decisions

Agreed with the backend team:

1. **The paths stand.** `POST /api/v1/applications` and
   `POST /api/v1/route-selections`, with `v1` in the path.
2. **The backend owns rate limiting.** The frontend contributes the honeypot
   field and nothing else. On `429` the form shows one general message and
   keeps the entered values, so the applicant can retry.
3. **The confirmation email belongs to the backend** and carries the concrete
   next step. The screen carries none of it. See
   [the confirmation section](#the-confirmation-screen-needs-nothing-from-the-server)
   for why that makes the email mandatory rather than optional.
4. **`consentTextVersion` is stored**, and the wording of each version gets a
   home a reader can find.
5. **`POST /api/v1/route-selections` will be built.** It is the only
   measurement of `A5` this project will produce.

## Deployment shape

The prototype runs on **our own domain**, deployed by us. It is not part of
`ichbinhier.eu` and the association owns none of it — the point is to show them
what the platform would look like.

That decides two things for the backend:

- **One reverse proxy, one origin.** The form's static files and the API are
  served from the same host, so no CORS configuration is needed at all. Do not
  add permissive CORS headers "just in case"; they would only be needed if this
  shape changed.
- **The demo database holds test data only.** The consent text in `DESIGN.md`
  section 23 names ichbinhier e.V. as the party that stores the applicant's
  details, and on our own domain that is not who receives them. Real
  applications must not be collected here: seed the database, reset it, and keep
  the deployment out of public reach.

If the association later hosts the platform themselves, both points change and
the consent text becomes accurate as written.
